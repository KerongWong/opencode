## 问题

OpenCode Desktop V2 现有三种界面模式，没有一个以「项目」为组织单位：

- **Top tabs**：浏览器式标签，管理的是「打开过的 tab」。
- **Side tabs**：同一批打开过的 tab 竖排，仍是 tab 列表，不是项目视图。
- **Inbox**（实验性）：按「需要你处理 / 进行中 / 最近 / 归档」聚合，是按**状态**排。

项目只出现在 Home 的项目选择器（用于过滤）和会话元数据里。当同时在跑 4–9 个项目时，找「上周那个改 CI 的会话」只能靠打开或悬停逐个确认。上游 issue #55446、#60241 提的是同一件事，都还开着。

目标：新增第四种模式，左栏结构为 **项目 → 该项目的历史会话（默认 5 条 + Show more）→ 点击打开**，默认选中最近修改的会话。

## What Makes This Cool

不是"多了一层折叠列表"，而是把桌面端的默认假设从「我在管理 tab」换成「我在几个项目之间切换」。打开即看到我的项目全貌，第一个动作就是继续干活，不需要先回到 Home 找项目。

## 约束

按优先级：

1. **与上游长期共存。** 你会反复 merge `anomalyco/opencode`。改动面积 × 上游改同一文件的概率，是首要成本。
2. **不出 bug 比功能完整重要。** 你原话：「不会有什么不顺手的，就是怕你这边改完会出bug。」
3. 只改桌面端 `packages/app`，不动 `packages/server`、`packages/protocol`、数据库、TUI。
4. 个人 fork，不追求上游评审口味，不需要通用配置项和国际化全覆盖。
5. 默认每项目展示 5 条会话，超出折叠为 `Show more (N)`。

## Premises

1. 做成**第四种模式**，不改现有三种；`interfaceMode` 增加一个值（暂称 `projects`）。
2. 只改 `packages/app`，不新增后端能力。
3. 会话数据复用 Home 已在用的同一份索引，侧栏不另造列表、不存副本。
4. 左栏结构固定：项目 → 会话（5 条 + more）→ 点击打开；打开动作复用现有入口。
5. 默认打开**最近修改**的会话（按更新时间，不按创建时间）。
6. 不属于任何项目的会话（临时会话、未选目录）归入固定的 `Ungrouped` 分组，不能消失。
7. 不做：跨项目活动流、拖拽排序、会话多项目归属、TUI 同步。
8. 所有上游文件的改动收敛为一张**接缝清单**；接缝之外全部是新文件。

## Approaches Considered

### Approach A：最小接缝的内置第四模式

新增 `packages/app/src/projects/**`（全部新文件），只在 3 处上游文件各加几行：`interfaceMode` 枚举加值、设置页加一个单选项、shell 布局多一个分支。数据复用现有会话索引。

- 冲突面：3 处、合计约 10 行
- 风险：低（不碰 tab 状态机）
- 成本：S–M

### Approach B：GUI 插件形态（零官方文件改动）

用 `@opencode/plugin/gui/host` 的 renderer 入口（内置插件均为 `main + renderer` 双入口，见 `packages/gui-plugins/src/renderer.ts`）把项目树挂进侧栏。

- 若成立：上游合并零冲突，且插件坏了不会拖垮主程序
- 未验证：宿主是否开放侧栏插槽、第三方 GUI 插件能否被加载
- 风险：插件 API 变动会连带失效
- 成本：M（先半天 spike）

### Approach C：外挂工作台

不改 UI，直接读本地 session 存储，做独立窗口/面板。零冲突，但不是主窗口左栏，体验与 DSH 差一截。已排除。

### 会话中途排除的做法

- 改 `shell/tabs/*` 让它按项目分组：动 tab 状态机（拖拽排序、恢复、快捷键），冲突与 bug 都从这来。
- 顺手改 i18n 大字典 / appearance 页：上游每次发版都在动，小改动也会持续冲突。

## Recommended Approach

**走 A：最小接缝的内置第四模式。** B 已经验证完毕并排除（见下节），零冲突路径在本需求上不存在；A 的接缝已被压缩到 3 处、约 10 行。

### Spike 结论：B（GUI 插件）不可行

验证对象：`packages/plugin/src/gui/registries.ts`、`host.ts`（dev 分支）。

| 判定项 | 结论 | 证据 |
| --- | --- | --- |
| 1. 第三方 GUI 插件可被加载 | **成立** | host 的 enable 规则区分 builtin 与 bundle，非 builtin 按保存的行解析 |
| 2. 存在可挂侧栏内容的插槽 | **不成立** | `SlotMap` 仅有 `window.bottom`、`session.header`、`session.location.menu`、`session.panel.end` |
| 3. 插件可读项目与全部会话 | 未验证（第 2 项已否决） | — |
| 4. 插件可触发打开会话 | 未验证 | — |
| 5. 插件可持久化折叠状态 | 未验证 | — |

补充证据：`Panel.region` 的类型只有 `"side"`，注释为 "tabs in the side region's strip"——即会话右侧面板的标签条，不是应用左栏导航。应用左栏由宿主（shell）自己渲染，插件无法接管。

结论：第 2 项不成立即判定 B 失败。若未来宿主新增左侧导航插槽，可重新评估；在当前 dev 分支上不再重复验证。

### A 的接缝清单（实施时按真实代码确认行号）

| 接缝 | 预期改动 | 冲突面 |
| --- | --- | --- |
| `interfaceMode` 枚举/类型 | 增加一个值 | 1 行 |
| 设置页接口模式单选项 | 增加一个选项 + 文案 | 1–3 行 |
| shell 布局分派 | 增加一个分支指向新组件 | 1–3 行 |
| i18n（可选） | 个人 fork 可不进字典，直接写中文/英文常量 | 0 行 |

规则：**只增不改**，不改格式、不重排 import、不顺手修上游代码。每次合上游后按此表逐项检查，而不是重新推理。

### 实施顺序（三个原子提交）

1. `feat(app): add projects interface mode value and shell dispatch` —— 只为让一个空侧栏能显示，验证不破坏现有三种模式。
2. `feat(app): project-grouped session sidebar` —— 纯展示组件 + 纯函数分组/排序，自带单测。
3. `feat(app): default to most recently updated session in projects mode` —— 冷启动选择逻辑。

UI 组件全部放在新目录 `packages/app/src/projects/`，只有第 1 个提交碰上游文件，冲突面可单独 cherry-pick 或回滚。

## Open Questions

1. `interfaceMode` 枚举定义在哪个文件，是否被持久化到磁盘配置（决定旧版本回退时会不会报错）。
2. 会话索引里项目归属用哪个字段（`projectID` / `directory` / worktree 路径），多 worktree 是否算同一项目。
3. "最近修改"取 `updated`、`time.updated` 还是最后一条消息时间；有运行中会话时该字段是否实时更新。
4. 每个项目的会话总数是否需要额外查询（若索引只返回首页数据，`Show more` 需要分页）。
5. 冷启动时"默认打开最近修改的会话"是否会和"恢复上次会话"冲突，以哪个为准（前提 5 暂定最近修改）。

## Success Criteria

- 切到 Projects 模式后，左栏按项目分组正确，项目内按更新时间倒序。
- 点击会话能在主区打开，内容与从 Home 打开一致。
- 新建 / 重命名 / 删除会话后，左栏无需手动刷新即保持一致（最迟 1s）。
- 无项目会话出现在 `Ungrouped`，不会消失。
- 切回 Top tabs / Side tabs / Inbox，行为与改动前完全一致。
- 冷启动默认打开最近修改的会话。
- 合一次上游 `dev` 后，冲突文件数 ≤ 3，且都在接缝清单内。

## Distribution Plan

## The Assignment

在写任何代码之前先做一件事：**在你的 fork 里跑一次 `git merge upstream/dev --no-commit`，记录冲突文件，再 `git merge --abort`。**

现在分支干净，这次空跑只回答一个问题：上游最近有多活跃地改 `packages/app/src/shell` 和 `settings`。如果这两处是高频区，第 2 步的挂载点要重新想（比如从路由层分派，而不是布局层）；如果不活跃，就按现方案直接做。

把结果（冲突文件数、最近 30 天 `shell/` 的提交数）追加到本文档末尾，再开始第 1 步。
