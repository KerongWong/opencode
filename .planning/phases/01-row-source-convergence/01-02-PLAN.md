<objective>
Give the Projects sidebar one bounded row source: locally known sessions may only join rows that are already indexed or are at least as recent as the index window, with a known-only fallback when no index exists.

Purpose: SRC-02. Today `mergeRootSessionIndex` lets any session this process loaded add a row, so opening old history injects project rows and the row set is not reproducible across restarts. The bound makes the row set a function of the server page while keeping new sessions visible and keeping the offline list.

Output: `mergeRootSessionIndex` implements `boundedKnown`, `createSessionInbox` passes it for the Projects view only, `session-index.test.ts` proves the drop, the boundary, the new-session path, the offline list, restart parity, and the Inbox archived row the bound would drop, and `packages/app/perf/session-index.bench.ts` measures the merge against `origin/dev`.

Planner-settled decision (no CONTEXT.md exists for this phase):

- **D2 — the bounded `known` window, Projects only.** Compute `floor` as the smallest `time.updated` among indexed rows. When the index has rows and `boundedKnown` is set, a known root may contribute only when its id is already indexed or its `time.updated` is at or above `floor`. When the index has no rows, known roots are the list (the SRC-03 offline contract). Chosen over a pure id intersection because an intersection would hide a session created in this process until the next refetch and would fail the offline contract; chosen over an unconditional `known` pass-through because that is today's bug.
  - **Per-view window.** `createSessionInbox` passes `boundedKnown: options.archived !== true`. The Projects view (`createSessionInbox()`, `archived` unset) gets the floor window over its single `inbox-sessions` page (at most `INDEX_LIMIT` rows). The Inbox view (`createSessionInbox({ archived: true })`) merges up to two pages — `inbox-sessions` plus `inbox-archived-sessions` — so a floor over that merged list is not a meaningful window, and that view keeps every known row it already had. The two views therefore do not share one window; only Projects is bounded.
  - **Archived invariant.** The Inbox row's archive action calls `move()`, which removes the row from `inbox-sessions` and only prepends to `inbox-archived-sessions` when that query already has cached data. When it does not (the archived page was never loaded in this process), the known archived row is the only source for `sections().archived` in `inbox.tsx`. Disabling `boundedKnown` for that view is what keeps it; with the bound enabled, a row below the floor would vanish and the Archived section would disappear. So the bound is never allowed to drop a known archived row from the Inbox view. The merge-level test pins that drop (`boundedKnown: true` removes the row) so the reason for the per-view choice is executable; the controller's option mapping itself is not unit-tested because `createSessionInbox` needs the Solid runtime and server context, and the manual archive check stays in `<verification>`.
  - **Restart reproducibility:** with a reachable server the Projects row set depends only on the server's newest root sessions plus their archive state, so a fresh process (empty `known`) derives the same rows. Bounded known can only add rows at or above the existing floor, which are the rows the index page itself is about to return.
  - **Deliberately drops:** a known root older than the floor never sources a Projects row (it stays reachable through Home, the Inbox view, and the command palette). The offline fallback is process-local and therefore not restart-stable; that degradation is intentional and bounded by `known()`.
- **D1 / D3** were settled in plan 01-01: archived filtering is an option on the same pure merge.
- **Dependency:** plan 01-01 already added `RootSessionIndexOptions` with an inert `boundedKnown` field and the `includeArchived` filter. This plan activates `boundedKnown` and must not change the archived behavior.

Facts the plan relies on (re-read each file before editing):

- `data.session.known` is the client's full known-session list (`runtime/server/data.ts:100`) and grows whenever this process loads a session, including sessions far older than the 50-row index.
- The index query returns the newest root sessions (`INDEX_LIMIT = 50`, `order: "desc"`, `parentID: null`); `parseHomeSessionIndex` drops archived rows from that page.
- `mergeRootSessionIndex` currently copies every known row into the row map; the `passive` branch only controls whether the indexed `time.updated` is preserved, never whether the row joins.
- `entries()` is the hot path: it recomputes on every session event and every second while a session works (`inbox-model.ts` clock effect). The bound adds one integer comparison per known row and one `reduce` over at most ~50 indexed rows (`Math.min` per row; no array is materialized for the floor). The third-argument options object is one small literal per recompute. `packages/app/perf/session-index.bench.ts` measures the merge against `origin/dev` (task 3).
- `shell/commands/palette.ts` calls `mergeRootSessionIndex(known, loaded)` with two arguments and must keep its current behavior; the default `boundedKnown` is off.
- Inbox's archived rows come from `inbox-archived-sessions` only when that page is cached: `move()` prepends there only while `current` is truthy, and `forget()` removes the row from `inbox-sessions` first. On a cache miss the known archived row is the only source, and `inbox.tsx` gates its Archived button on `list.some(inboxArchived)`. That is why the Inbox view does not use the bound.
